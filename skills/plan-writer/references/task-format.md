# Task format

The single definition of the task list shape. Used by plan-writer (in `plan.md`) and by spec-writer when `feature.json.separate_plan == false` (appended to `spec.md` as unnumbered sections). Read `task-decomposition.md` and `sizing-heuristics.md` for how to decompose and size.

## Per-task fields

- **Tag:** one stack token `frontend | backend | mixed`, optionally plus `owner` and/or `content`, comma-separated (e.g. `(backend, content)`, `(owner)`). See "Owner and content tasks".
- **Touches:** comma-separated glob list of files the implementer is expected to write (required; prefer narrow globs; list shared files explicitly).
- **Depends on:** prerequisite task IDs (e.g. `Task 1, Task 2`) or the literal `none` (required).
- **Size:** `S|M|L` (optional, after `Depends on`; missing means `M`; informational only).
- **Files:** paths to create/modify, where known.
- **Recipe:** `<recipe name>` (content tasks only; required for them; must exist in `profile.recipes`).
- **Wireframes:** relative paths from the feature folder, one per wireframe-anchored AC the task covers. Omit the field entirely if none.
- **Acceptance:** AC ids covered.
- **Steps:** checkbox list, only when an implementer would benefit.

## Structure

```markdown
## Tasks
- [TODO] **Task 1** (backend): <name>
- [TODO] **Task 2** (frontend): <name>

## Execution plan
- Group 1 (serial):   Task 1, Task 2     — foundation
- Group 2 (parallel): Task 3, Task 4, Task 6
- Group 3 (serial):   Task 5             — depends on 3 & 4

## Task details

### Task 1: <name>  `[TODO]`
**Tag:** backend
**Touches:** `api/posts/**`, `api/types.ts`, `db/migrations/**`
**Depends on:** none
**Size:** M
**Recipe:** <recipe name>  (content tasks only)
**Files:** ...
**Wireframes:** wireframes/<screen>.html  (omit if none)
**Acceptance:** AC<n>, AC<m>
**Steps:**
- [ ] ...
```

## Execution plan overview

The `## Execution plan` overview is documentation only. The orchestrator does NOT trust it at runtime: it recomputes groups at dispatch time from each task's raw `Touches:` and `Depends on:` fields. Keep it in sync as a courtesy; the per-task fields are the source of truth.

## Owner and content tasks

Both are allowed in track `full` only.

- `owner`: a manual step for the project owner. Never dispatched. Still needs `Touches` and `Depends on`. Example tag: `(owner)`.
- `content`: generated by a recipe. Must carry `**Recipe:** <recipe name>`, and that name must exist in `profile.recipes`. Combine with a stack token, e.g. `(backend, content)`.
